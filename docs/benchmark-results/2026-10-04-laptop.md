# Laptop run, 2026-10-04

## Machine

- Intel Core Ultra 7 255H (16 logical CPUs), 31 GB RAM, Windows 11 26100, Python 3.14.6.
- Postgres 18 with pgvector 0.8.1 (`pgvector/pgvector:0.8.1-pg18`) in Docker Desktop on the same laptop, default
  settings. Every query crosses the Docker Desktop network bridge.
- Model: `BAAI/bge-small-en-v1.5` (fastembed's ONNX build), onnxruntime 1.30 on the CPU.

## Search under load

`uv run python -m benchmarks.search_load --dsn ... --profile full --concurrency 16 --seconds 15`, against the full
evaluation collection (11,122 chunks), 16 concurrent clients, query vectors computed up front so this is the database
side of search: both retrievers, fusion and snippets.

| mode | searches/s | p50 ms | p95 ms | p99 ms |
|---|---|---|---|---|
| lexical | 353 | 37.3 | 96.0 | 143.7 |
| vector | 681 | 22.6 | 32.1 | 38.4 |
| hybrid | 209 | 64.7 | 143.7 | 223.9 |

Embedding the query adds 19 ms for a single query (10.8 ms each when batched).

Lexical search is the slower half, not the vector search. The OR query matches thousands of chunks for a typical
question and Postgres ranks every match with `ts_rank` before taking the top 50, where the HNSW index stops after
`ef_search` candidates. That is the price of the OR query (ADR 2). If it ever matters, the first thing to try is ranking only the top few thousand matches by a cheaper proxy.

## Embedding throughput

Measured on 256 development-set paragraphs (133 tokens on average, 416 at most):

| batching | paragraphs/s |
|---|---|
| batches of 64, in arrival order | 9.1 |
| batches of 8, in arrival order | 13.3 |
| batches of 16, sorted by length | 18.5 |
| batches of 8, sorted by length | 17.0 |

Sorting by length before batching (each batch is padded to its longest member) doubled throughput, and is what the
indexer does now. Building the full evaluation index (11,122 chunks) took 25 minutes in one indexer process while other
work shared the CPU. More indexer processes divide that.

The CPU is fast (a 2000 x 2000 float32 matrix multiply takes 43 ms), and the quantised and full-precision ONNX builds of
the model ran at the same speed: the model is simply a lot of arithmetic per 133-token paragraph on a laptop.

## What these numbers do not say

- Nothing about a Linux server or a managed Postgres.
- Nothing about corpora much larger than 11,000 chunks, where the HNSW index's memory and the lexical ranking cost both
  grow.
